# 真人出版复审的明确结论与版本记录

日期：2026-09-10。本次由用户委托 Codex 执行工程与页面验证；未登记真人审校或个人学习证据。

## 问题与最终行为

旧接口只有验收者与说明，系统把有效说明直接计为通过；数据库每构建、每阶段只能有一条记录，页面隐藏已记录阶段，导致补证后不能正常追加真人复审。

现在使用 `inkwords.human-publication-review.v2`：新记录绑定冻结 manifest，明确真人来源、阶段版本、结论、0–4 整数评分、范围、说明、证据与阻断发现。通过至少 3 分、有证据且没有阻断；需要修改必须写明发现；未评估以 0 为传输占位、页面显示未评分。旧说明、原时间均保留，不推断为通过。

同阶段复审通过 `expected_revision` 追加；旧记录算版本 1。同 ID/同输入重试返回原记录，相同 ID 改内容、过期前序或不同 manifest 返回 409。冻结构建行锁串行化追加；已晋级构建不能追加，原请求仍可精确重试。核心与导出共用完整历史检查，缺版本、冲突、错误来源/构建均阻断；最新需要修改的发现不能被另一来源的通过记录抹除。

页面保持八个阶段可选，展示完整历史、旧说明和明确评分。保存期间禁止编辑和二次提交；网络错误保留草稿与请求。刷新历史不自动改变未确认请求的前序版本；版本冲突后须核对新证据，再修改草稿。真人来源只接受实际人的记录，AI 委托入口继续独立。

写入 API、字段预算与操作步骤见 `docs/runbooks/textbook-publication-checklist.md`。

## 迁移与恢复

生产 core schema 已从 36 升至 37。新增显式决策列；旧行新列为 NULL，仅阶段版本默认 1。唯一索引由 `(build_id, stage)` 替换为 `(build_id, stage, revision)`，保留完成时间索引。新索引每次追加写一次，空间随审校版本数量增长；不声称固定八行上限。

实际生产对参数化 `SELECT COALESCE(MAX(revision),0) ... WHERE build_id=$1 AND stage=$2` 的 EXPLAIN 使用 `human_review_build_stage_revision` 的 Index Only Scan。当前表为空，此证据仅证明现有计划与索引适用性，不代表大数据吞吐。隔离测试另核验旧记录+复审历史下的索引可用性。

迁移测试实际在 PostgreSQL 运行：先应用原 17 表结构，插入旧说明，再升至 37；原字段 JSON 完全一致，决策/评分仍为 NULL。只有旧行时 Down 可成功；写入 v2 后 Down 明确拒绝并保留两条历史。生产迁移前全库真人记录为 0，表结构与数据备份在 `publication-reviews-before.sql`；迁移后仍为 0。

已有 v2 证据时必须保留 v2 解析和判定器，不可降级到把旧说明当通过的服务，也不可删除新列/新行以完成回滚。需要恢复时使用已核验备份并先处理备份后产生的证据。旧版已晋级构建若仅有无结论说明，新的预检不会补造通过；本机没有这类存量真人记录，因此该存量业务恢复未作生产操作。
