纠正提案已完成领域重放验证，尚未由用户采用、未写入学习记录。候选服务尚未部署。

## 最终实现

原 v6 请求把 metadata.answer 序列化成空字符串，同时又在 assessment-answer 中提供
非空正文。真实模型曾据此把完整作答评为“作答为空”。新请求移除 answer/evidence 空
字段，使用 answer_evidence_id 明确指向唯一的作答正文及其原输入 hash，不复制参考
答案作为作答。通过失败测试复现了空字段，再验证新请求只有一个作答来源。

原 InputHash、作答字节、rubric 和来源保持；v6 新请求 hash 因组装修复发生变化。
旧 v1–v5 路径保持，原 v5 四份请求 hash 实际对比一致。已保存反馈的身份与纠正历史
不重写，旧预览不能冒充新请求；持久化仍比较原预览的 InputHash/RequestHash。

低强度推理在 3000 输出 Token 下仍可能没有有效反馈，因此新增显式、有上限的
Options.MaxOutputTokens。默认仍为 3000，新配置最多 6000，非法预算在调用前拒绝；
预算进入预览和请求 hash。最终评测选择 low + 6000，模型仍为 deepseek-v4-flash，
45 秒适配器/60 秒外层超时、一并发、零自动重试保持。生产 bootstrap 尚未启用它。

曾尝试让模型从连续原文片段列表中选引文；该限制拒绝了本已通过逐字校验的合法引文，
且增加请求体积，因此已从产品代码撤回。源码、hash 和失败收据存放在
output/real-acceptance/2026-09-06/quote-enumeration-experiment-source/，不是上线候选。
最终继续接受任意合法的连续原文引文，不放松伪引文、来源或运行证据门禁。

## 自动语义复核与提案

四例通过数值门槛不等于每句建议都正确。原结果保持，另行提出三份纠正：

1. 完整答案：补救建议写出了不存在于来源的 EnableHandleMethodNotAllowed，并把
   methodTrees.get 写成未经来源证明的请求调用点。改用来源中的 HandleMethodNotAllowed，
   分别追踪登记和请求分派，不编造两者调用关系；下一步提示补入请求分派来源。
2. 不完整答案：已说出“查找路由，然后执行处理函数”的粗略过程，完整性从 0 提议改为 1，
   仍明确缺少注册、按方法/路径分派与命中边界；同步修订遗漏理由。提议平均分为 0.4。
3. 误解答案：保留原分数，修正完整性理由，将“没有准确给出流程”与“错误描述未登记
   路径”分开，不能将已经说错的内容描述为完全没有提及。

提案位于 output/real-acceptance/2026-09-06/single-answer-correction-proposals-v1/。
每份包含原收据 hash、原有效反馈 hash、修改内容和拟生效反馈 hash，明确标记
automated_correction_proposal / pending_user_review。领域重放验证三份提案、原文不变
和过期 hash 拒绝；验证中的虚拟 reviewer/time 不导出为人工审阅记录。模型原分数和
判断没有被修改，Provider 调用 0、人工审阅 0、学习记录写入 0。
