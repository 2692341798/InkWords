# InkWords 学习与教程编写平台产品需求文档（PRD）

> 版本：V1.1 需求基线
>
> 状态：已完成需求与教材质量基线，待用户确认和开发排期
>
> 更新日期：2026-09-02
>
> 产品口号：把高密度资料加工成真正学得会、讲得清、可出版的系统教材。

## 1. 产品定位

InkWords 是一个供个人在本机使用的学习与教程编写平台。它从公开 GitHub 仓库、对应官方文档以及本地资料中提取可追溯证据，将晦涩但知识密度高的技术资料加工为通俗、专业、可运行、可练习的中文系统教材。

平台只维护一份“教材母稿”，并从母稿派生三类用途：

1. 可继续编辑和投稿出版的教材稿；
2. 可拆分发布的系列技术博客及录屏操作教案；
3. 供作者本人学习、复述、编码、排错和间隔复习的训练材料。

V1 是单用户、本机运行的生产工具，不是面向公众的在线教育平台，也不要求移动端安装包或公网服务器。

## 2. 产品目标与成功标准

### 2.1 核心目标

- 将多个高门槛资料源加工成结构完整、初学者能跟做、专业读者也认可的教材。
- 让同一份内容能够服务出版、博客、自媒体录屏和个人学习，避免重复写作与内容漂移。
- 用可执行代码、运行结果、调试和资源观测证明教材内容，而非仅生成流畅文字。
- 用复述、补全、从零实现、需求变更和故障定位检验掌握程度，并根据表现安排复习。
- 在不牺牲核心质量的前提下，通过检索、缓存、分阶段生成和局部重生成降低 Token 消耗。

### 2.2 V1 成功标准

- 能以 Gin GitHub 仓库、Gin 官方资料和 Go 官方资料为证据，生成一套面向零基础学习者的中文教材。
- 能走通“资料导入 → 全书大纲审批 → 样章审批 → 按章生成 → 代码验证 → 教材编辑 → 学习评测 → 到期复习 → 多格式导出”的完整闭环。
- 每个重要事实、代码示例和运行结论均可回溯到来源或验证证据；无法验证的内容必须明确标记。
- 已批准或人工修改的内容不会被 AI 静默覆盖。
- 相同资料和相同生成阶段可以复用本地缓存，并能查看每章 Token 用量及缓存命中情况。

### 2.3 非目标

V1 明确不做：

- 注册、登录、验证码、GitHub OAuth、JWT、多用户与权限系统；
- 公网部署、SaaS、团队协作、付费订阅和内容市场；
- Android、iOS、HarmonyOS、Windows、macOS、Linux 原生安装包；
- 来源更新监控、自动增量同步和旧教材自动迁移；
- 自动搜索或引用第三方博客、论坛、问答站和聚合内容；
- 自动操控 VS 2022、GoLand 等跨平台桌面软件并完成截图；
- 完整教材的中英双语维护；
- EPUB 导出和复杂出版排版系统。

## 3. 用户与使用环境

### 3.1 目标用户

唯一目标用户是 InkWords 的本机拥有者，同时具有三种身份：教材作者、自媒体教程制作者和学习者。

### 3.2 运行方式

- 沿用当前 React + Go 服务的本地浏览器模式，通过 Docker Compose 一键启动。
- 默认仅从本机入口访问，不要求配置公网服务器。
- 用户自行配置 DeepSeek 或 OpenAI API Key。密钥只能保存在本地安全配置中，不得写入教材、日志、仓库或导出包。
- V1 保留数据库及必要后台任务，但所有业务默认属于同一个本地工作空间，不再通过用户身份隔离。

## 4. 核心概念与内容模型

### 4.1 教材项目

“教材项目”是顶层工作单元，包含资料源、目标读者、全书蓝图、章节、验证证据、训练任务、导出配置和生成用量。

一本教材可以组合多个资料源，但必须指定一个主资料源。主资料源决定版本与主叙事，其他官方资料作为补充证据；冲突无法自动消解时必须提示人工判断。

### 4.2 教材母稿

教材母稿是唯一内容事实源。以下产物不得维护相互独立的正文副本：

- 教材/出版稿；
- 系列博客；
- 视频操作教案；
- 学习卡片、练习和复习题。

它们应引用相同的章节、代码、插图、证据和术语，只在编排和呈现方式上派生。

### 4.3 系列与章节

一本教材天然也是一个系列，一章可作为一篇独立博客发布。章节必须既能独立阅读，又保持全书前置依赖、术语、示例项目和难度递进的一致性。

### 4.4 内容状态

教材项目和章节至少支持：`草稿`、`候选稿`、`已批准`、`需补证`、`验证失败`。

- AI 重生成只能创建候选稿并展示差异。
- 人工修改或已批准章节默认锁定。
- 只有用户明确应用候选稿后，母稿才能被替换。
- 不实现复杂版本树；来源重新导入时创建新的教材项目，旧项目和学习记录不变。

### 4.5 整本教材合同

蓝图批准时同时冻结可版本化的 BookContract，作为全书生成与审校的共同合同，至少包含：

- 读者画像：已掌握、未掌握、容易误解的知识，操作系统、开发工具和可投入时间；
- 全书承诺：学完后能独立完成的任务，以及本书明确不覆盖的范围；
- 部、章、节层级，概念地图、先修依赖图和由浅入深的学习路线；
- 贯穿项目、每章起止代码状态、统一运行环境和依赖锁定策略；
- 章节类型、预计学习时间、篇幅与认知负荷预算；
- 术语表、命名规则、语气、标点、数字、单位、代码、图表、引用和答案样式；
- 前置内容、正文、附录、答案、参考文献、索引等原稿组成；
- 出版目标、引用格式、版权策略及出版社特别要求。

修改 BookContract 后，系统必须指出受影响章节、资产和验证结果；不得无提示地让新旧规则混在同一部书中。

## 5. 资料输入与证据边界

### 5.1 支持的输入

- 公开 GitHub 仓库，可选择分支、标签或提交；导入时记录并固定最终提交 SHA。
- 公开 HTTPS 官方文档站，可抓取指定入口下的完整文档栈。
- 本地 PDF、DOCX、Markdown、TXT 和 ZIP。
- 同一教材可混合使用上述来源。

### 5.2 官方资料限定

- 教材生成只使用用户导入的主资料，以及对应项目或技术栈的官方资料。
- 系统可以联网识别和确认官方入口，但不能自动采用第三方内容。
- 第三方博客、论坛、问答、搜索摘要和聚合站不得进入生成证据集。
- 官方资料的判定、补充与移除应对用户可见并可人工调整。

### 5.3 整站抓取边界

- 仅抓取公开、无需登录的 HTTPS 内容。
- 默认限制在用户确认的域名和路径前缀内；站外链接只记录，不跟随抓取。
- 尊重站点的 robots 约束、访问频率和明确许可范围。
- 支持 HTML、Markdown、纯文本，以及页面中链接的 PDF、DOCX、TXT、Markdown 和 ZIP。
- 对规范化 URL、重定向、重复正文和内容哈希进行去重。
- 保存标题、URL、抓取时间、内容类型、版本线索、父子导航和内容哈希。
- 对抓取页数、单页大小、总下载量、抓取深度、并发和超时设置可配置上限；达到上限时输出缺失清单，不得假装完整。
- 不绕过登录、付费墙、验证码、访问控制或反爬限制。
- 防止 SSRF、私网访问、危险重定向、压缩炸弹、路径穿越、恶意文件和文档中的提示注入。

### 5.4 本地文件与 ZIP 边界

- 单文件大小上限沿用现有 888 MB 约束，但解析器还必须分别限制解压后总大小、文件数、目录深度和单成员大小。
- ZIP 仅提取白名单文档和代码文本文件，拒绝可执行文件、符号链接逃逸及路径穿越。
- 原始文件保留在本机资料库，供重新解析、引用校验和出版溯源；不得发送无关全文给模型。
- 解析失败必须保留原因和可重试入口，不能把空内容当作成功资料。

### 5.5 快照与更新策略

V1 在导入时形成一次固定快照，不监控上游变化。若官方文档或仓库以后更新，由用户手动重新导入并创建新的教材项目。

## 6. 教材生产流程

### 6.1 创建项目

用户选择主资料和补充官方资料，设置技术主题、目标成果、主要读者层级、教材深度及默认模型。系统先给出资料清单、版本、覆盖范围和解析风险。

### 6.2 构建本地资料索引

系统解析资料、代码结构和导航关系，按语义与结构切分，生成可检索的本地证据索引、术语表、API/符号索引和来源账本。后续调用只检索当前任务所需片段，禁止默认把整站或整个仓库塞入提示词。

### 6.3 生成全书蓝图并人工审批

蓝图至少包含：

- 教材定位、目标读者和完成后的可观察能力；
- 前置知识与零基础补偿路径；
- 章节顺序、依赖关系和每章学习目标；
- 贯穿全书的示例项目与阶段成果；
- 每章需要引用的证据、运行验证和演示工具；
- 练习、排错和复习覆盖计划；
- 预计篇幅、生成批次和 Token 预算估算。

用户批准蓝图前，不允许批量生成章节。

### 6.4 生成代表性样章并人工审批

用户选择或由系统推荐一章作为完整样章。样章必须完成内容、代码验证、运行结果、练习、视频教案和来源引用。若全书同时包含概念原理、操作实践、源码导读、项目实战等不同章节类型，系统再为未被完整样章覆盖的主要类型生成短篇风格探针。用户批准样章和必要的风格探针后，其表达风格、深度、术语和版式成为后续章节的生成契约。

### 6.5 按章生成

- 默认按需生成，不自动一次性生成整本书。
- 用户可以在样章批准后选择批量生成剩余章节。
- 每章独立检索证据、生成、验证、审校和记账；失败不影响已完成章节。
- 章节生成状态至少显示：检索证据、生成草稿、事实核验、代码验证、教学审校、生成候选稿、等待批准、完成或失败。

### 6.6 人工编辑与局部重生成

- 沿用 Markdown 编辑和浏览器语音转文字能力。
- 支持选区、内容块或单章级重生成，不因局部修改重做全书。
- 重生成前展示原因、使用证据与预估消耗；完成后提供差异对比。
- 批量操作不得覆盖锁定章节。

### 6.7 全书合成与编辑流水线

章节完成不等于原稿完成。整本候选原稿必须依次经过：

1. 发展性编辑：检查全书承诺、内容取舍、章节顺序、先修依赖和难度递进；
2. 技术审校：检查事实、源码、命令、实验、边界和安全性；
3. 自学性审校：检查隐藏前提、术语首次出现、步骤跨度、反馈和独立完成路径；
4. 全书一致性审校：检查术语、交叉引用、图表编号、代码版本、重复与矛盾；
5. 文字编辑：按 StyleSheet 统一语言、标点、数字、单位、格式和引用；
6. 排版后校对：在 DOCX/PDF 实际版面中检查目录、页码、断页、代码、图片、题目和答案；
7. 出版合规预检：汇总版权、授权、署名、敏感内容、书名页元数据和待出版社确认事项；
8. 人工终审：用户明确批准后才标记为“出版候选原稿”。

系统可以用不同上下文的 AI 审校和确定性检查辅助上述流程，但不得把 AI 自审标记为人工同行评审、出版社审稿或法律合规认证。

## 7. 自学型教材内容标准

### 7.1 “可自学”的定义

“可自学教材”是指目标读者在没有教师现场补充的情况下，仅依靠教材及其明确提供的资料，就能完成以下闭环：

1. 知道本节学什么、为什么现在学以及完成标准；
2. 检查前置知识，并在不足时获得就地补偿或明确跳转；
3. 用已有经验建立直觉，再学习准确术语和机制；
4. 按连续、无隐藏步骤完成示例并核对中间结果；
5. 通过解释、预测、练习、迁移和排错暴露自己的误解；
6. 根据分层提示修正错误，并知道下一步学什么；
7. 脱离原文复述或重做，若干天后仍能通过复习验证。

以下“防自学”写法属于质量缺陷：

- 用术语解释术语，或在定义前连续使用缩写和专业名词；
- 只说“是什么”，不说为什么出现、解决什么问题和为何有效；
- 大段罗列 API、配置或源码，却不交代调用时机、数据流和预期结果；
- 省略安装、权限、目录、版本、输入、保存、重启等关键步骤；
- 使用“显然”“很简单”“不再赘述”“读者自行研究”代替必要解释；
- 示例跨度过大，只展示最终代码，不解释每次变化；
- 把罕见高级细节放在主线前面，阻断完成最小闭环；
- 只有答案没有诊断反馈，读者出错后不知道错在哪里或如何恢复。

### 7.2 自顶向下与渐进展开

- 先给全局地图：系统要完成什么、主要组件是什么、一次请求或一次操作如何走完全程；再逐层进入组件、算法、数据结构和源码。
- 先用日常语言说清概念，再给出准确专业术语；术语一旦引入，全书保持同一含义。
- 采用“整体 → 局部 → 重新组装整体”和“具体场景 → 抽象规律 → 新场景迁移”的双向结构。
- 主线先交付最小可运行闭环；高级原理、历史细节、特殊优化放入明确的进阶块，移除进阶块后主线仍可独立学习。
- 每节原则上只引入 4–6 个新的核心元素；超过时应拆节、建立分组或插入回顾，但不得为了满足数量而割裂天然整体。
- 每节提供预计时间、当前所在位置、完成检查点和下一节衔接，避免读者失去全局方向。
- 抽象机制优先同时提供文字、图示、最小代码和实际观测；图示不能代替可访问的文字说明。

### 7.3 符合自然学习规律的节奏

InkWords 不假设所有人共享一条固定的“自然学习曲线”。系统根据目标读者的前置知识和实际表现组织以下可循环、可调节的学习路径：

1. **唤醒旧知识**：用一两个问题或小任务确认读者已有的概念，并补齐本节真正需要的前置知识；
2. **制造真实需要**：让读者先经历或观察旧方法的限制，产生学习新技术的明确理由；
3. **先见整体**：给出结果预览、系统地图和本节在全书中的位置，避免一开始陷入局部细节；
4. **具体示范**：使用完整 worked example 展示专家如何思考、操作、检查和纠错；
5. **带扶手练习**：让读者预测下一步、补全局部并立即核对，提示由弱到强；
6. **逐步撤除脚手架**：从模仿、补全过渡到只给目标和约束，不让读者永久依赖教程；
7. **独立解决与迁移**：更换输入、需求或故障，让读者在新情境中重建方案；
8. **复述与连接**：用自己的话解释因果链，并把新知识连接到已学概念网络；
9. **间隔与交错复习**：在若干天内重新提取知识，并与相近、易混知识交错练习；
10. **依据证据调整**：根据正确率、提示次数、耗时、错误类型和复述质量，缩小步幅、补偿前置知识或提高挑战。

教材采用“螺旋式深入”：第一次只建立能工作的准确模型，后续在真实需要出现时再回到同一概念，补充源码、性能、异常和设计权衡。后续内容可以修正早期模型，但必须明确说明早期简化了什么，不能让前文成为需要推翻的错误知识。

难度应位于“有挑战但可恢复”的区间。连续失败时提供更小步骤、额外例子和前置补偿；连续轻松完成时减少提示、增加变式和迁移。不得用突然出现的大型综合任务、无提示的环境问题或故意晦涩的表述制造伪难度。

### 7.4 统一质量骨架

每章必备：

1. 本章要解决的问题及实际价值；
2. 前置知识检查与必要补偿；
3. 可检验的学习目标；
4. 直观心智模型、专业原理和适用边界；
5. 至少一个从输入到输出的完整示例；
6. 可跟敲的代码步骤与每步预期结果；
7. 先预测再揭示的理解检查；
8. 同类练习、答案或判分标准；
9. 常见错误、故障现象、定位路径和修复方法；
10. 修改需求的迁移练习；
11. 用自己的话复述的费曼任务；
12. 本章总结、术语表、来源和后续复习任务。

每章应优先从一个具体、可信的任务场景切入，让读者先理解“为什么现在需要这个知识”，再进入术语和机制。例如：误删代码后需要恢复、两名开发者同时修改同一处代码产生冲突、线上接口突然变慢需要定位资源消耗。场景必须服务于本章学习目标，不能只作为无关故事或标题噱头。

每章的核心技术点必须完成“技术理解六问”，不得只介绍定义、命令或 API：

1. **为什么需要**：在什么历史背景或真实场景下，原有做法遇到了什么限制；
2. **解决什么问题**：明确问题、约束、受益者，以及不使用该技术时可观察到的失败或成本；
3. **有哪些实现方法**：列出主流实现层次和路线，比较工作位置、核心机制、优势、代价及选型条件；
4. **如何使用**：选择一条适合当前场景的路线，给出最小可运行示例、操作步骤、输入输出和适用条件；
5. **为什么有效**：解释从用户操作到内部组件、数据结构、协议或运行时行为的关键链路；
6. **何时不该使用**：说明代价、边界、常见误用和替代方案。

讲解顺序遵循“先看到问题，再引出技术；先建立直觉，再解释机制；先完成最小使用，再观察底层行为；最后迁移和排错”。底层原理不能停留在抽象描述：应尽可能通过日志、调用链、网络请求、进程、线程、文件变化、内存、CPU、数据结构或源码定位，让读者看到技术在系统里实际发生了什么。无法直接观测的部分必须标明其证据来源或推断边界。

这套标准适用于命令、语言特性、框架、数据库、中间件和系统架构等所有技术主题。例如讲解负载均衡时，不能只给出 Nginx 配置：应先用单个服务实例在流量增长或故障时出现排队、超时和不可用的场景说明为什么需要；再解释它解决流量分配与可用性问题，但不能消除后端总容量、共享数据库瓶颈或应用缺陷；比较 DNS/全局流量调度、四层转发、七层反向代理、客户端负载均衡和服务网格等实现路线；随后让读者启动多个可识别的服务实例并完成一种最小实现；通过请求日志、实例标识、并发压测、延迟、吞吐量和健康检查切换观察请求如何被分配；最后解释轮询、加权、最少连接、哈希与一致性哈希、健康检查、连接复用、反向代理、会话一致性、重试放大及负载均衡器自身高可用等底层机制和边界。

### 7.5 章节类型与按需模块

章节至少区分以下类型，并分别定义必选内容块，避免所有章节机械套用同一模板：

- 概念原理章：问题演进、心智模型、机制、边界和概念辨析；
- 操作实践章：环境、连续步骤、中间检查点、结果和恢复路径；
- 源码导读章：调用入口、关键结构、控制流/数据流、调试与生产权衡；
- 项目实战章：需求、设计决策、迭代代码、测试、变更和复盘；
- 故障诊断章：现象、假设、证据、定位路径、根因、修复和预防；
- 复习整合章：知识网络、综合任务、混合练习和迁移；
- 参考附录：可检索的准确资料，不承担首次教学任务。

第 7.4 节的内容是覆盖清单，不要求每章以十二个固定标题机械呈现。安装配置、IDE 操作、断点调试、浏览器开发者工具、性能分析、内存/CPU/网络观测、源码追踪和综合项目只在主题和章节类型需要时出现。

### 7.6 三种读者版本

每个教材项目先选择一个主要版本：

- 零基础：补充环境、语法、术语和每一步操作，降低单步跨度。
- 有编程基础：省略通用基础，强调技术栈概念、模式与工程实践。
- 熟悉技术栈：强调源码、设计权衡、性能、边界和迁移能力。

三种版本共享事实、证据、代码资产、学习成果和章节关系，只改变讲解密度、脚手架和练习难度。V1 只先生成用户选定的主要版本，其他版本按需生成。

### 7.7 通俗语言与写作要求

- V1 只生成中文。
- 专业术语首次出现时给出英文原词；代码、命令、API 和标识符保持原样。
- 首次解释采用“通俗说法 → 准确定义 → 例子/反例 → 与相近概念的区别”；禁止用尚未解释的术语构成循环定义。
- 句子优先短而完整，一段只承担一个主要意思；动词说明谁执行什么动作，避免连续名词化、无主体被动句和为显得专业而堆砌形容词。
- 缩写首次出现时写出中文含义和英文全称；同一小节出现过多新缩写时必须拆分或提供就地提示。
- 每段理论之后回答“这对当前任务有什么用”，每段代码之后解释关键变化和运行时发生了什么。
- 精确不等于晦涩。能用常用词准确表达时不用生僻词；专业词无法替代时必须解释，而不是删除必要专业性。
- 面向零基础读者时采用“任务场景 → 风险或冲突 → 生活化类比 → 准确机制 → 动手验证 → 类比边界”的叙事顺序。可以把 Git 描述为“程序员的时间回溯工具”，但随后必须准确解释提交、工作区、暂存区、引用和恢复命令的真实行为。
- 类比必须显式指出相似点与不相似点。例如“两名粉刷匠反复覆盖同一堵墙”可以帮助理解协作冲突，但不得写成 Git 能阻止两人修改同一段代码；应进一步说明 Git 如何发现差异、自动合并或要求人工解决冲突。
- 场景中的人物、风险和操作应贴近真实开发，但不得依赖羞辱、恐吓或不必要的夸张推动学习；重点是让读者理解后果和恢复路径。
- 采用原创讲解和自行设计的示例，不大段搬运或近似改写来源。
- 结论必须区分：来源事实、实际观测、机制解释和合理推断；推断需说明边界。
- 禁止输出模型思考过程、对话式前言、虚构引用和未经验证的运行结果。

### 7.8 教材质量量表与硬门禁

每章和整本候选原稿按 0–4 级分别评价：技术正确性、证据完整性、因果解释、自学可用性、示例可复现性、认知负荷、全书一致性、语言清晰度、原创性与出版完整性。`0` 表示缺失或危险，`1` 表示存在严重缺陷，`2` 表示需要重写，`3` 表示达到候选原稿要求，`4` 表示表现优秀。

进入“已批准”前必须没有任何硬失败项，且各维度不得低于 3。以下任一情况直接硬失败：

- 关键事实无证据、证据与结论不匹配或把推断写成事实；
- 可执行示例未通过验证，或运行结果与当前代码版本不一致；
- 存在隐藏前提、危险操作无警告、无法恢复的错误步骤；
- 前置知识顺序错误、同书定义冲突、代码状态断裂或引用失效；
- 术语堆砌、循环定义、关键因果跳步导致目标读者无法独立继续；
- 教学实现冒充生产实现，或没有说明省略能力与适用边界；
- 引用、代码、图片、字体或截图缺少必要权利信息；
- 题目无法从已教内容作答，答案本身错误或泄漏在题目前。

质量报告必须显示每个维度的证据、缺陷位置和修改建议，不能只给总分。评分合同和阈值需要版本化；规则变化时只重新评估受影响内容。

## 8. 代码、运行结果与视觉证据

### 8.1 代码验证

- 当核心机制适合用代码表达时，章节必须提供一份“从零实现”的最小教学源码，而不只是配置文件或调用第三方 API。源码应将原理中的关键步骤映射到具体函数、数据结构和执行流程，并配套测试、运行命令及可观察结果。
- 教学源码必须标记为“教学实现”，明确省略了哪些生产能力，不得暗示可以直接用于生产环境。随后应基于固定版本的主资料或官方源码，定位至少一条生产实现路径，解释它如何处理并发、超时、故障、安全和性能等复杂问题。
- 不要求复制整份上游源码。生产源码讲解使用仓库版本/提交、文件、符号和行号定位，只摘取许可证允许且理解所必需的片段，其余通过链接、调用图或文字解释。
- 对无法安全、合理地从零复现的内核、驱动或分布式设施，可使用受控模拟器或缩小模型，但必须说明模型与真实系统的差异。
- 当前环境可执行的示例必须在隔离工作区中完成格式化、编译、测试或最小运行验证。
- 验证不得直接修改导入的原始项目。
- 保存依赖版本、操作系统/运行时、执行命令、退出状态、关键输出和时间。
- 无法运行的示例必须标记“未运行验证”并解释原因；失败示例不得作为正确答案发布。

负载均衡教学源码至少应包含：后端节点池、可替换的选择策略、请求转发、超时、健康状态和并发安全；基础版本实现轮询，再通过测试或实验加入加权、最少连接或一致性哈希中的至少一种。章节还应指出教学版本未覆盖的连接池、协议细节、重试预算、慢启动、异常实例摘除、配置热更新和负载均衡器高可用等生产问题。

### 8.2 教材中的运行结果

- 稳定且适合复制的结果以文本输出块呈现。
- 界面状态、调试过程、内存/CPU/网络变化、浏览器行为等以截图或图示呈现。
- 截图必须具有步骤、环境、说明文字和可替代文本，不能只放图不解释。
- 图、表、代码清单和公式分别连续编号并支持稳定交叉引用；标题说明“读者应从中看出什么”，正文必须实际解释该证据。
- 信息图不得只依赖颜色表达差异；复杂图提供长描述，表格使用明确表头，代码与终端图片同时提供可复制文本。
- 架构图、调用图和内存图必须绑定所解释的版本、范围与简化假设，避免把概念示意图冒充真实运行结构。
- 运行结果应与产生它的代码版本绑定，代码变化后原结果自动标记为待复核。

### 8.3 截图采集边界

- V1 可自动采集受支持的终端输出和浏览器截图。
- 对 VS 2022、VS Code、GoLand、桌面调试器和性能分析器，系统生成拍摄清单，由用户操作并上传或粘贴截图。
- 系统检查所需截图是否齐全，并将已确认截图编排进教材与视频教案。

## 9. 视频操作教案

视频教案是教材母稿的录屏视图，主要显示在副屏上指导主屏录制，不是独立文章。

每个可录制步骤应包含：

- 步骤编号与教学目标；
- 建议讲述的话术要点；
- 应使用的工具及选择理由；
- 精确操作，如菜单路径、按钮、快捷键、命令和输入内容；
- 预期画面、运行结果与异常分支；
- 需要放大、停顿、截图或对比的位置；
- CPU、内存、调用栈、网络等观测指标及其解释边界；
- 常见失败、恢复动作和进入下一步的检查点。

系统根据技术栈和任务自动推荐 VS 2022、VS Code、GoLand、浏览器开发者工具、终端或相应分析器。V1 只生成可编辑的操作方案，不自动控制桌面 IDE。

## 10. 学习、评测与复习闭环

### 10.1 主动学习方式

- 阅读教材原文与代码；
- 使用键盘或现有浏览器语音功能完成复述；
- 补全关键代码；
- 不看答案从零实现；
- 根据新需求修改实现；
- 对故障样例进行定位和修复。

浏览器语音只负责本地语音转文字，后续与键盘文本进入相同评测流程；V1 不上传、保存或管理音频。

### 10.2 六级掌握证据

1. 解释：能用自己的话说明原理和边界；
2. 补全：能补齐核心步骤或代码；
3. 复现：能脱离教程从零实现；
4. 迁移：能按变更后的需求修改方案；
5. 诊断：能定位并修复典型故障；
6. 保持：若干天后仍能通过复习测试。

只有取得“保持”证据后，知识点才显示为已掌握。阅读完成或一次答对不能等同于掌握。

### 10.3 评测与反馈

- 复述根据准确性、完整性、因果关系、边界条件和表达清晰度评分。
- 编码根据正确性、完整性、可运行性、测试结果和关键设计判断评分。
- 排错根据假设质量、定位路径、证据使用、根因和修复验证评分。
- 反馈必须明确列出答对内容、遗漏、误解、下一步提示和补救材料。
- 提示遵循由弱到强的层级，优先促使回忆，不立即泄露完整答案。

### 10.4 自适应复习

- 系统根据每次复述、编码和排错表现动态计算下一次复习时间与任务类型。
- 薄弱点缩短间隔并增加针对性练习；稳定掌握后逐步延长间隔。
- 每次调度需要保存依据，允许用户查看并手动调整。
- 只有用户主动打开 InkWords 时才展示到期任务；V1 不发送系统通知、不后台常驻提醒。

## 11. 知识库与来源治理

- 继续采用 Karpathy LLM Wiki 方式管理个人知识。
- 原始资料进入 `.raw/` 或等价只读资料区；来源卡片、概念和实体分别归档并建立链接。
- 教材项目引用知识库内容，但不得无提示地改写原始资料。
- 教材关键结论维护来源账本：来源类型、标题、URL/文件、版本或提交、定位、许可证、引用用途和验证状态。
- 正文仅显示必要脚注，导出时生成完整参考资料及许可证清单。
- 授权不明确的内容标记“出版前需人工确认”，不阻止仅限个人的学习和验证。
- 对正文、代码、图片、截图、图标、字体、商标和第三方数据分别维护权利清单，记录作者/权利人、许可证或授权依据、允许用途、是否修改、署名方式和出版状态。
- “公开可访问”“官方资料”“GitHub 上可见”和“允许出版使用”不能互相替代；权利依据不充分的材料不得进入出版候选原稿，可保留为仅限个人学习的证据。
- 系统进行相似片段和连续引用提示，但只能作为人工版权审查线索，不能声称自动判定合理使用或不存在侵权。

## 12. 导出与再利用

### 12.1 V1 导出格式

- Markdown：母稿和系列博客的长期可编辑格式；
- DOCX：投稿、出版社协作和人工审校的主要交换格式；
- PDF：版式检查、审阅和样稿展示；
- ZIP：打包 Markdown/DOCX/PDF、图片、代码、练习答案、来源清单和视频教案。

EPUB 延后到后续版本。

### 12.2 导出要求

- 可导出整本教材、单章或选定章节。
- 系列博客按章节拆分，同时保留前后篇导航和全书目录。
- 视频教案可独立导出，但其内容仍引用母稿步骤和资产。
- 导出前运行完整性检查：未验证代码、缺失截图、待确认许可证、断裂引用、未批准章节和失败任务必须汇总展示。

### 12.3 出版候选原稿组成

出版候选原稿按 BookContract 生成，并至少支持：

- 书名、作者、内容简介、目标读者、前置知识和“如何使用本书”；
- 前言、目录、正文、附录、术语表、答案/提示、参考文献和版本记录；
- 插图与表格清单、代码清单、示例工程与运行环境说明；
- 来源账本、版权/授权清单和需要出版社判断的问题清单；
- 可编辑 DOCX、审阅 PDF、母稿 Markdown 及完整资产 ZIP。

系统不得伪造 ISBN、CIP/在版编目数据、出版单位、责任编辑、出版日期或印刷发行信息。正式书号、书名页和版权页内容以合作出版单位最终要求为准。

### 12.4 中国大陆出版预检基线

以中国大陆正式图书出版为默认目标时，InkWords 只提供原稿质量与合规预检，不替代出版单位的选题、编辑责任、三审三校、质量检查或法律判断。预检规则必须显示来源、版本和检查日期，并允许按出版社要求切换：

- 内容与出版流程遵循届时有效的《出版管理条例》及出版单位要求；
- 著作权、改编、复制、信息网络传播、代码许可证、图片/截图和字体使用遵循届时有效的法律、许可证和授权文件；
- 中文标点默认检查 GB/T 15834—2011，数字默认检查 GB/T 15835—2011，量和单位检查现行国家标准；
- 参考文献默认支持当前有效的 GB/T 7714—2025，也允许出版社指定其他著录体例；
- 按《图书质量管理规定》的正式图书编校质量要求生成差错清单，以不超过 1‱ 为最低预检目标，但不得把自动检查结果表述为官方质量认定；
- 对 AI 参与方式保留生成来源和人工修改记录；是否以及如何披露，以投稿时的法律、主管部门和出版社要求为准。

上述标准发生修订时不得静默沿用旧规则；系统应提示用户更新出版检查配置。出版社约定与默认规范冲突时，记录偏离原因并以合法、明确的出版社要求为交付准则。

## 13. 模型调用与 Token 优化

### 13.1 模型接入

- 使用用户自己的 DeepSeek 或 OpenAI API Key。
- 通过统一模型接口提供任务级配置，包括资料分析、蓝图、章节生成、技术审校和学习评测。
- 用户选择默认模型或任务档位；系统不得在未提示的情况下自动切换到更昂贵的模型。

### 13.2 生成策略

- 先生成全书蓝图，再生成一章样章，通过两个人工门禁后才允许批量生成。
- 默认按章、按需生成；修改时优先选区或内容块级局部生成。
- 检索与当前任务相关的证据包，不把整个资料库重复发送给模型。
- 将稳定规则、教材契约、来源摘要和动态任务分层组织，提高提供商缓存命中率。
- 资料切分、内容摘要、证据包、蓝图、章节和评测结果均以内容哈希缓存；输入或生成契约变化时精确失效。
- 机械工作优先本地完成，如解析、去重、索引、引用校验、格式转换、代码执行和确定性规则检查。

### 13.3 用量可见性

- 展示每个任务、章节和教材项目的输入 Token、输出 Token、缓存命中/未命中、模型及预估费用。
- 生成前显示估算，生成后显示实际值；估算与实际不可混淆。
- 用户可取消任务和配置并发上限。
- 不设置会直接截断核心讲解或降低事实质量的统一硬额度；超出预估时应先暂停并让用户选择。

## 14. 本地、安全与可靠性要求

- 默认仅暴露本机访问入口，服务端口和数据库不得无意对局域网或公网开放。
- API Key 与敏感配置不进入日志、提示词审计正文、导出物或 Git。
- 所有网络抓取和模型调用显示目标域名、状态和失败原因。
- LLM 输出和导入文档均视为不可信数据，不能把其中指令当作系统命令执行。
- 代码验证在受限、可清理的隔离工作区运行，具有网络、CPU、内存、进程数、磁盘和超时限制。
- 长时解析、生成、代码验证与导出采用可取消、可恢复查看的后台任务；浏览器刷新不应造成任务状态丢失。
- 错误信息使用中文，保留可诊断原因，不泄漏密钥与内部敏感信息。
- PostgreSQL 和资料/导出目录使用本地持久化卷，并提供明确的备份与恢复说明。

## 15. 关键页面与信息架构

V1 主导航收敛为：

1. 教材项目：创建、导入资料、查看项目状态；
2. 教材工作台：蓝图、章节树、母稿编辑、证据、验证和导出；
3. 学习与复习：到期任务、复述、编码、迁移与排错；
4. 知识库：Obsidian/LLM Wiki 状态及导入导出；
5. 设置：本地模型、API Key、抓取边界、执行环境和用量。

旧“博客”能力并入教材工作台：一章即一篇可发布博客，不再维护独立于教材的系列生成主流程。手写内容仍可作为空白教材项目或章节创建。

## 17. 验收场景

### 17.1 主验收：Gin 零基础教材

输入：

- 主资料源：`https://github.com/gin-gonic/gin` 的固定提交；
- 官方补充资料：Gin 官方文档与 `https://go.dev/` 范围内经用户确认的页面；
- 读者层级：零基础；
- 输出语言：中文。

必须证明：

- 整站/仓库资料清单、范围、版本和缺失项可见；
- 蓝图未经批准不能批量生成；
- 样章包含必备质量骨架、可运行代码、真实输出和来源；
- 样章能展示“旧知识激活 → 问题体验 → 整体预览 → 示范 → 带扶手练习 → 独立迁移 → 复述复习”的学习闭环，并能根据表现调整步幅和提示；
- BookContract 能明确读者已知/未知知识、全书承诺、先修依赖、章节类型、认知负荷、术语和出版样式；
- 样章未经批准不能批量生成剩余章节；
- 至少一处浏览器或终端自动证据、一处 IDE 人工截图清单能正确进入教材；
- 人工修改的章节在重生成时不会被覆盖；
- 一名符合目标画像的试读者或作者以“冷启动试读”模式，在干净环境中不依赖口头补充完成样章；系统记录卡点、隐藏前提、错误、耗时和恢复情况；
- 学习者能完成复述、代码补全、从零实现、需求变更、故障定位和延迟复习；
- 到期任务只在打开 InkWords 时出现；
- 可导出 Markdown、DOCX、PDF 和包含完整资产的 ZIP；
- 整本候选原稿通过术语、先修依赖、重复/矛盾、交叉引用、代码连续性、图表编号、版权和编校预检；
- 出版候选原稿包含前置内容、正文、附录、术语表、答案、参考文献、版本记录和待出版社确认清单，且不伪造 ISBN/CIP/出版单位信息；
- 可查看每阶段 Token、缓存和费用数据；
- 断网或模型失败时，已导入资料、已批准章节和学习记录仍可访问。

### 17.2 次验收：C++ 官方资料

使用 `https://isocpp.org/tour` 与 `https://isocpp.org/get-started` 验证官方站抓取、资料索引和蓝图生成。V1 不要求完成整本 C++ 教材。

## 18. 产品验收原则

- “已生成”不代表“已完成”：需同时通过来源、事实、代码、教学结构和人工审批门禁。
- “读完”不代表“已掌握”：需通过解释、补全、复现、迁移、诊断和延迟保持。
- “看起来合理”不代表“已验证”：所有执行和观测声明必须附真实证据，否则明确标记未验证。
- “支持整站”不代表“无限抓取”：必须有清晰范围、资源预算和缺失报告。
- “节省 Token”不代表“压缩质量”：优先消除重复输入、无关上下文和不必要重生成。
- “讲过”不代表“讲懂”：每个核心技术点都必须回答技术理解六问，并由方案比较、最小示例、底层观测、迁移练习或排错任务证明。
- “专业”不代表“难懂”：专业性来自准确、完整和边界清楚，不来自术语密度；无法让目标读者独立继续的内容必须重写。
- “章节合格”不代表“全书合格”：还需通过全书一致性、编辑、校对、冷启动试读和出版预检。
- “出版候选”不代表“正式出版”：书号、编目、内容审读和最终质量责任属于依法开展出版活动的出版单位及相关责任主体。

## 19. 规范依据与维护方式

本 PRD 的教学与出版基线参考以下官方或机构原始资料，系统实现时应记录检查日期，不把链接内容全文注入普通生成任务：
